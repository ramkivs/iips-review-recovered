## 1. Objective
Establish whether actual-data presentation is demonstrable: capture the API mode inputs,
prove the mode-UI component cluster, and record the browser-observed mode badge
(ACTUAL / REFERENCE / DEGRADED) reconciled against W13 actual coverage —
`frontend/src/features/user-portfolios/portfolioMode.ts` + `PortfolioModeIndicator.tsx`

coverage; today REFERENCE/DEGRADED is the honest badge.

## 11. Evidence capture
`12-W17/<id>/output/`: `api-*.json`, `w17-component-cluster.log`, `browser-checklist.json`,
`browser\` screenshots (seal afterwards with `New-StlEvidenceManifest.ps1`).

## 12. Evidence validation
`browser-badge-recorded` + `badge-consistent-with-evidence` checks; manifest verify after
sealing screenshots.

## 13. Result classification
PASS = API + component legs green + browser badge recorded and consistent; BLOCKED = API/UI
down; INCONCLUSIVE = legs done but browser checklist not yet completed; FAIL = badge
inconsistent with evidence (e.g. ACTUAL without full W13 actual coverage — a defect to
investigate, never re-labelled).

## 14. Downstream impact
PASS establishes whether actual-data presentation (incl. ACTUAL mode) is demonstrable —
completes W17's outstanding real-data browser/API acceptance input.

## 15. Unsuccessful / unavailable evidence
- UI not running → BLOCKED for the browser leg (API leg still runs); resume = `npm run dev`.
- No W13 report → `w13-actual-coverage-known` records fullyValued=false; ACTUAL badge would
  then be inconsistent → FAIL by design. Resume = complete step 08 (needs 04 → daemon/B02).
- Existing API captures verify via manifest; new browser pass required only when the evidence
  (revision, coverage) changed.
