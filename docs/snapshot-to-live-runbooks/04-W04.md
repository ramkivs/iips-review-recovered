## 2. Capture-summary integration (corrected shapes)
The W03/W02 sanitized capture summary provides `portfolio.revision`,
`portfolio.holdingsCountReported` and `portfolio.holdingsArrayLength`. It does **not** carry
`portfolio.holdingsCount` — the script never reads that field from the summary.

The accepted revision-1 baseline is identified **deterministically by capture-id prefix**
(`-AcceptedCaptureIdPrefix d1992178`, `-AcceptedCaptureRevision 1`) via
`Find-StlAcceptedCaptureOfRecord` — not by "last summary encountered". Zero matches → recorded
problem; more than one → *ambiguous*, recorded problem; the run does not silently pick one.

The latest live W03 evidence is identified **by execution id**
(`-W03ExecutionId STL-02-W03-20261125T100309Z`) via `Get-StlW03ExecutionEvidence`, reading
`<EvidenceRoot>\snapshot-to-live\02-W03\<id>\result.json` (result / `manifestVerifyOk` /
`failedCheckCount`) and `output\capture-summary.json` (revision, holdings via
`holdingsCountReported`/`holdingsArrayLength`).

## 3. Revision availability — comparison basis corrected
`maxRevisionInHistory` from the revisions route is compared against the **accepted
capture-of-record revision (1)** — never against the W03 revision (4).

| Field | Meaning |
|---|---|
| `maxRevisionInHistory` | exact max revision in the live revisions route |
| `acceptedCaptureOfRecord` | captureId + revision 1 of the accepted 2026-11-22 capture |
| `latestW03Evidence` | execution id, result, manifestVerifyOk, revision 4, holdings 65 |
| `comparisonBasis` | states the comparison is vs accepted revision 1 |
| `relationshipToAcceptedCapture` | `4 > 1` ⇒ newer revision exists — **revision availability only**; it does **not** establish that any holding's identity evidence changed |
| `subsequentRevisionExists` | boolean, recorded — never assumed |
| `holdingsWithChangedIdentityEvidence` | not determinable from revision numbers alone — needs a fresh `CONSISTENT_CAPTURE` of the newer revision + per-holding stored-`securityIdentity` diff |
| `missingInput` | fresh capture of the newer revision (IPD G3 bound, B02-class host access) + per-holding identity diff |

For the known W03 evidence: **revision 4 > accepted revision 1** ⇒ `subsequentRevisionExists = true`
(revision availability). The accepted 1/64 census remains the historical baseline and is not
re-labelled.

## 4. Cardinality reconciliation — 64 vs 65 (investigated, evidence-backed)
`output/cardinality-reconciliation.json` records three distinct populations:

| Population | Count | Basis |
|---|---|---|
| Accepted census rows | **64** | `DHAN_PORTFOLIO`-scoped coverage rows measured at revision 1 (§16.286) |
| Latest live portfolio holdings | **65** | W03 revision-4 capture (`holdingsCountReported`/`holdingsArrayLength`) |
| Coverage-route total items | **65** | served response = 64 `DHAN_PORTFOLIO` rows **+ 1 AIIL default-portfolio item** (other-portfolio rows are excluded from the census and recorded, not dropped) |

**Finding:** the 64-vs-65 difference is a *population* difference, not an API/data-contract error:
the coverage route intentionally spans all portfolios (the extra AIIL item), the census scopes to
`DHAN_PORTFOLIO`, and the portfolio population grew from 64 (revision 1) to 65 (revision 4) via
later MERGE revisions. The three counts are recorded separately and never silently equated.

## 7. Result classification
PASS = census reconciles (64/1/63), enumerations written, three bases recorded, revision
availability recorded vs accepted revision 1, W03 manifest verification read from the exact
execution's `manifest-verify.json`. BLOCKED = API down / W05-STEP1 absent. FAIL =
e.g. live resolved identity ≠ accepted without an identity-supplying revision — that contradicts
§16.286 and must be investigated, not re-labelled. When the W05 capture failed, the route basis
is recorded UNAVAILABLE (null counts, `ROUTE_UNAVAILABLE`) and W04 can never be PASS on that
run: a fresh execution with a successful `CAPTURED` route capture is required.
