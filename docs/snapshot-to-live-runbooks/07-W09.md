# Runbook 07 — Sequence 6: W09 actual persisted-data read path and revision consistency

**Script:** `06-w09-readpath-verify.ps1`

## 1. Objective
Verify the actual persisted-data read path through the IRR API transport: two full read cycles
plus a fresh read-only capture, all revision-consistent — W09 actual-data acceptance input
(with W02 concurrency and W03 counts; tracker §16.324/§16.325).

## 2. Repository locations
IRR routes used by W09: `/api/user-portfolios/:id` (detail envelope — carries revision,
provenanceDigest and the EMBEDDED holdings collection) and `/:id/revisions`. There is NO
separate holdings-route GET in W09 (`userPortfolioBoundary.ts` — malformed/missing revisions
are refused, never repaired);
capture CLI under `frontend/server/user-portfolio/capture/`. IPD: G3 provider owns the store;
IPD #150 (`0b6a0bea`) wraps v1/v2 reads in `withReadSnapshot` on IPD main.

## 3. Input identification
`-PortfolioId DHAN_PORTFOLIO`; env names `IIPS_G2_IPC_ENDPOINT`, `IIPS_G3_IPC_BINDING_PROVISIONED`
in the window (for the fresh capture).

## 4. Prerequisites
00-preflight PASS; API healthy; G3 pipe present + bound.

## 5. Runtime requirements
IRR API (:8787) + IPD G3 provider (for the capture). No UI, no daemon.

## 6. Startup instructions
Per `01-PREFLIGHT.md` §6.

## 7. Basic checks
`/api/health` 200; pipe probe; capture exit 0.

## 8. Execution procedure
```powershell
powershell.exe -NoExit -ExecutionPolicy Bypass -File .\06-w09-readpath-verify.ps1
```
(a) fresh read-only capture into the package; (b) two API read cycles, each exactly TWO GETs
(detail envelope + revisions, preserved verbatim as detail.json / revisions.json; holdings are
read from the embedded `portfolio.holdings` in the detail response); (c) consistency: same revision + digest across both
cycles (equality booleans only) and vs the capture, holdings counts equal, exactly one history
entry at the returned revision; (d) disclosed limitation recorded: `sources.ts:128-140`
list-then-get may read different revisions per portfolio — no cross-service atomicity is
asserted (roadmap rule).

## 9. Scripts / invocation
`06-w09-readpath-verify.ps1 [-TimeoutSeconds 300]`.

## 10. Expected output
`output/read-cycles/cycle-{0,1}/` (detail.json + revisions.json per cycle), `cycles-summary.json`, `capture-summary.json`,
`RESULT [PASS]`.

## 11. Evidence capture
`06-W09/<id>/` package; the fresh capture's LOCAL-ONLY exact file stays on the host inside the
package dir and feeds steps 08/09/11.

## 12. Evidence validation
`cycles-same-revision`, `cycles-same-digest`, `revisions-history-single-entry`,
`capture-vs-api-*` checks; manifest verify.

## 13. Result classification
PASS = all consistency checks hold; BLOCKED = capture/API/pipe absent; FAIL = any
inconsistency (investigate; never repaired or re-labelled).

## 14. Downstream impact
PASS gives W09 its actual persisted-data read-path evidence and produces the capture ref
consumed by **W13 (step 8), W16 (step 11), W17 (step 12)** and cross-checked by W03 (step 2).

## 15. Unsuccessful / unavailable evidence
- Provider down/binding refused (capture exit 10/11) → BLOCKED; API cycles still run and are
  recorded; resume = bound provider + re-run. If a prior consistent capture exists, steps
  08/09/11 can still reuse it; otherwise they report BLOCKED naming the missing capture.
- Revision changed between cycles → FAIL (INCONSISTENT_READ semantics); the correct response is
  investigation on the IPD side; a re-run after the store settles produces a new consistent
  capture (new capture required in that case).
