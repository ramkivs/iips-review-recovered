### F9-6 symlink capability and safe scope

The unavailable case is creation of a **file-entry symbolic link** inside the generated acceptance fixture. On Windows, creating one ordinarily requires the `SeCreateSymbolicLinkPrivilege` (commonly available to an elevated administrator), or unprivileged symlink creation enabled through Developer Mode on supported Windows 10 version 1703 (build 15063) or later, using an API path that requests the unprivileged-create flag. This is distinct from the non-elevated directory junction that did succeed. The runner uses Windows PowerShell 5.1 `New-Item -ItemType SymbolicLink` and catches inability to create the link as unavailable; verify that exact cmdlet succeeds on the selected test host rather than inferring capability from OS version alone. A junction does not exercise the file-entry check.

A safe completion would use only the targeted `-TestId F9-6` run on a disposable Windows VM/test host already configured with the needed symlink capability (either an approved unprivileged Developer Mode configuration or a test-only elevated token), keeping the created link and target entirely inside the runner's generated `%TEMP%` fixture. The test must demonstrate that the actual acceptance function rejects that file-entry reparse point. Do not enable Developer Mode, elevate or reconfigure the designated production host merely for this fixture without separate authorization. Do not change or weaken production reparse-point controls. Until the file-entry branch is actually exercised, retain **PARTIAL / NOT TESTED**.
